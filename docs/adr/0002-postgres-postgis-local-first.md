# PostgreSQL + PostGIS, local-first; schema as versioned SQL migrations

Status: accepted (2026-09-25, Phase 3)

The database is PostgreSQL 16 + PostGIS running in Docker locally, with
`EM_DATABASE_URL` as the only deployment-dependent value. Schema is managed
by handwritten numbered SQL files in `app/db/migrations/` applied by a small
runner — no ORM, no autogenerated migrations.

## Why

- **PostGIS was never optional**: AOIs are spatial objects; a geometry column
  + GiST index + `ST_Intersects` is the difference between "polygon search"
  and a pile of JSON math.
- **Local-first matches "private until stable"**: $0, zero external
  dependency, full PostGIS fidelity. When the site goes public (Phase 10),
  the same DSN points at Neon/Supabase — migrations are plain SQL and run
  identically anywhere.
- **Handwritten SQL > Alembic here**: the schema is the portfolio artifact;
  numbered `.sql` files are reviewable, diffable, and honest. Alembic's
  autogenerate saves effort only when the ORM owns the schema — ours doesn't.
- **SQLite+SpatiaLite rejected**: fine for a file-based demo, but the moment a
  web process + a worker write concurrently it becomes the bottleneck, and
  migrating off later rewrites every spatial call.

## Consequences

- ID policy: `uuid` PKs on user-facing resources (users, aois, devices);
  `bigint GENERATED ALWAYS AS IDENTITY` on append-heavy tables (scenes,
  metrics, notifications, ingestion_runs).
- `scene_aois` materializes the scene↔AOI spatial join at ingestion time —
  reads stay cheap, ingestion pays the spatial cost once.
- `metrics` is long-format with `UNIQUE (aoi_id, scene_id, metric_name)` —
  reprocessing is an idempotent upsert, never a dedup problem.
- Storage for rasters: none in v1 (TiTiler renders from provider COGs).
